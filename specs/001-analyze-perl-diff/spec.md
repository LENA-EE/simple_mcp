# Feature Specification: analyze_perl_diff

**Feature Branch**: `001-analyze-perl-diff`
**Created**: 2026-05-17
**Status**: Draft

## Контекст

PR-бот и pre-commit хук не хотят гонять `perlcritic` по всему файлу — это
дорого по времени, шумно по выводу и засоряет ревью техническим долгом,
который разработчик не писал в этом PR.

Нужен лёгкий тул, который смотрит **только добавленные строки в git diff**
и возвращает только новые нарушения. Стоимость PR-ревью падает в разы;
комментарии бот пишет точечно по тем строкам, которые разработчик реально
тронул.

**Граница ответственности vs соседние тулы:**

```
analyze_perl_critic        — полный аудит модуля (есть)
analyze_perl_diff          — этот тул, быстро, без контекста
analyze_perl_diff_smart    — с full_file контекстом (отдельная фича, требует mcp-bitbucket)
analyze_before_commit      — diff_smart + impact analysis через PPI (требует Symbol Index)
check_before_push          — pre-push гейт, только severity-блокировка (есть)
```

`analyze_perl_diff` намеренно **не видит контекст**. Это его сильная и
слабая сторона. Сильная — дёшево и быстро. Слабая — нарушения вида «новая
строка ок, но в сочетании со старым кодом баг» он пропустит. Для этого есть
`analyze_perl_diff_smart` отдельной спекой.

**ВАЖНО: severity в Perl::Critic — обратная шкала:**

```
severity=1 → СТРОЖАЙШИЙ (все нарушения, включая стиль)
severity=5 → только КРИТИЧЕСКИЕ
```

Тул следует этой инверсии (как и `perlcritic_analyze`).

## User Scenarios & Testing

### User Story 1 — PR-бот ревьюит небольшой diff (Priority: P1)

PR-бот получает webhook из Bitbucket → читает unified diff
изменённого `.pm` файла → дёргает `analyze_perl_diff(diff=...)` →
получает список нарушений **только в добавленных строках** с реальными
номерами строк итогового файла. Пишет комментарии в PR.

**Why this priority**: это основная причина существования тула — точечный
фидбек по PR без шума от технического долга.

**Independent Test**: подать тулу искусственный diff с одной добавленной
строкой `open(FILE, $path)` (severity 5) → проверить, что в ответе один
issue с правильным номером строки.

**Acceptance Scenarios**:

1. **Given** diff содержит `+open(FILE, $path);` на строке 52 нового файла, **When** PR-бот вызывает `analyze_perl_diff(diff=...)`, **Then** в `issues` ровно один issue с `line=52`, `severity=5`, `policy=InputOutput::ProhibitTwoArgOpen`.
2. **Given** diff содержит только контекстные строки (нет `+`), **When** бот вызывает тул, **Then** `count=0`, `issues=[]`, `error=None`.
3. **Given** diff содержит несколько hunks с разными добавленными строками, **When** бот вызывает тул, **Then** номера строк в `issues` берутся из соответствующих `@@ ... +X,Y @@` хедеров, не последовательно от 1.

---

### User Story 2 — Pre-commit хук разработчика (Priority: P2)

Разработчик настраивает локальный pre-commit хук, который читает
`git diff --cached` → отправляет на MCP → блокирует коммит при severity ≥ 4
в новых строках.

**Why this priority**: ценно, но не критично — `check_before_push` уже
закрывает дисциплину на уровне push. Pre-commit — улучшение DX, не безопасность.

**Independent Test**: тот же тул, тот же контракт; хук отдельной фичей.

**Acceptance Scenarios**:

1. **Given** разработчик добавил строку с severity 5, **When** хук вызывает тул и фильтрует `severity >= 4`, **Then** коммит блокируется с указанием строки.
2. **Given** добавлены только строки с severity 1–3, **When** хук вызывает тул, **Then** коммит проходит (если хук настроен на severity ≥ 4).

---

### User Story 3 — Diff без Perl-кода (Priority: P3)

В diff попадают изменения `.md`, `.json`, `.txt`. Тул не должен падать;
должен спокойно вернуть пустой `issues`.

**Why this priority**: устойчивость, не основной сценарий.

**Acceptance Scenarios**:

1. **Given** diff с изменениями только `.md` файлов, **When** тул вызван с этим diff, **Then** `count=0`, `error=None`. (Фильтрация по типу файла — на стороне вызывающего; этот тул просто прогонит `perlcritic` на извлечённых строках, которые не являются Perl-кодом — `perlcritic` вернёт 0 issues либо parse error, который нормализуется в пустой список.)

---

### Edge Cases

- **Diff с одними удалениями** (`-` строки, нет `+`) → пустой набор добавленных строк → `count=0`, `error=None`.
- **Diff с переименованием файла без изменения содержимого** → `+++/---`-хедеры есть, но `+`-строк после них нет → `count=0`.
- **Diff с binary-файлами** (`Binary files differ`) → не содержит hunks, парсер игнорирует → `count=0`.
- **Файл создан с нуля** (все строки — `+`, hunk `@@ -0,0 +1,N @@`) → корректно обрабатывается, номера строк 1..N.
- **Сломанный синтаксис в добавленных строках** (например, разработчик добавил начало функции без `}`) → `perlcritic` может вернуть parse error. Тул возвращает этот error в поле `error`, `issues=[]`. PR-бот сам решит, как поступить.
- **Diff содержит несколько файлов** → тул анализирует все добавленные строки склейкой; в issue поле `file` указывает на исходный файл из `+++`-хедера.

## Requirements

### Functional Requirements

- **FR-001**: MCP-тул `analyze_perl_diff` ДОЛЖЕН принимать `diff: str` (unified diff в стандартном git-формате) и опциональный `severity: int` (1–5, дефолт 1).
- **FR-002**: Тул ДОЛЖЕН извлекать только строки, начинающиеся с `+` и не являющиеся `+++`-хедерами файла.
- **FR-003**: Тул ДОЛЖЕН вычислять **реальные номера строк** добавленного кода в итоговом файле, парся hunk-хедеры `@@ -X,Y +A,B @@`. Номера строк в выходных `issues[].line` — это номера в итоговом файле, не в склееном blob'е.
- **FR-004**: Тул ДОЛЖЕН возвращать тот же формат ответа, что и `perlcritic_analyze`: `{path, type, issues, count, error, report_file, timestamp}`. Поле `report_file` всегда `None` (см. spec 003).
- **FR-005**: Если добавленных строк нет — ДОЛЖЕН вернуть `count=0, issues=[], error=None` без вызова `perlcritic`.
- **FR-006**: Тул ДОЛЖЕН регистрироваться в `tools/list` только если `PERLCRITIC_AVAILABLE=True` (как и `perlcritic_analyze`).
- **FR-007**: Тул ДОЛЖЕН быть устойчив к diff'ам, не содержащим Perl-кода: parse errors `perlcritic` нормализуются в пустой `issues` с заполненным `error`.

### Key Entities

- **DiffInput**: `{diff: str, severity: int = 1}` — входные параметры тула.
- **AddedLine**: `{file: str, new_line: int, content: str}` — внутреннее представление одной извлечённой строки.
- **DiffAnalysisResult**: тот же контракт, что у `analyze_perl_critic` (см. FR-004).

---

## Success Criteria

- **SC-001**: На искусственном diff с одной добавленной `open(FILE, $path)` в hunk `@@ -42,3 +52,4 @@` тул возвращает один issue с `line=52`.
- **SC-002**: На diff из 1000 строк (5 добавленных строк среди контекста) тул отвечает быстрее, чем `perlcritic_analyze` на полном файле в 1000 строк, минимум в 5 раз.
- **SC-003**: PR-бот может полностью заменить вызов `perlcritic_analyze` на `analyze_perl_diff` без потери покрытия новых нарушений (старые нарушения = технический долг, не комментируются — это фича, не баг).

---

## Assumptions

- Бот/хук формирует валидный unified diff через `git diff` или эквивалент (Bitbucket webhook payload).
- Один вызов тула обрабатывает diff произвольного количества файлов — фильтрация по типу `.pl/.pm` — на стороне вызывающего.
- `perlcritic` корректно работает на синтаксически неполных фрагментах Perl: возвращает либо issues по тем правилам, что отрабатывают лексически, либо parse error. Это допустимая «частичная» картина — именно ради скорости.

## Что НЕ входит в эту спеку

- **`analyze_perl_diff_smart`** — анализ с full_file контекстом, отдельная спека, требует `mcp-bitbucket` для чтения исходного файла.
- **`analyze_before_commit`** — diff_smart + impact analysis через PPI, отдельная спека, требует Symbol Index.
- **Pre-commit хук** — клиентский скрипт, отдельная задача после готовности тула.
- **Фильтрация diff'а по типу файла** на стороне сервера — это работа PR-бота / хука.
- **Поддержка не-unified diff форматов** (context diff и т.п.) — git везде использует unified, scope не расширяем.

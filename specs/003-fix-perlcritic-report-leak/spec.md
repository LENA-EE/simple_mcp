# Feature Specification: убрать утечку JSON-отчётов perlcritic на диск

**Feature Branch**: `003-fix-perlcritic-report-leak`
**Created**: 2026-05-17
**Status**: Draft

## Контекст

`tools/perlcritic.py` при каждом вызове `analyze_perl_critic` пишет JSON-отчёт на диск рядом с анализируемым файлом:

```python
# perlcritic.py:246-253
timestamp = datetime.now().strftime("%Y%m%d_%H%M%S")
report_filename = f"perlcritic_report_{base_name}_{timestamp}.json"
if os.path.isdir(target):
    report_path = os.path.join(target, report_filename)
else:
    report_path = os.path.join(os.path.dirname(target), report_filename)
```

Файл **никогда не удаляется**. Каждый вызов → новый timestamp → новый файл.

В режиме `code=...` (основной продовый режим, см. `CLAUDE.md` §4.2) отчёт падает в `/tmp/` контейнера. В режиме `target=<dir>` — в саму директорию анализируемого кода, что засоряет чужие исходники.

Содержимое отчёта уже возвращается через JSON-RPC ответ MCP. Файл на диске — дубль, который никто не читает.

## Проблема

**Утечка в проде:**
- Контейнер: `/tmp/` сидит в writable layer Docker (не tmpfs, см. `Dockerfile` — нет монтирования tmpfs).
- Команда ~10 человек × ~50 вызовов в день = ~500 файлов/день, ~15 тыс/месяц.
- Файлы переживают перезапуски контейнера, пока контейнер не пересоздан.

**Загрязнение пользовательских директорий:**
- При вызове с `target=<directory>` JSON-отчёт пишется внутрь этой директории.
- Если разработчик случайно укажет реальный путь проекта — отчёт окажется в его рабочих файлах.

**Несовпадение с принципом контекст-инженерии:**
- В `PROJECT_CONSTITUTION.md` §3 закреплено: «`raw_output` намеренно не отдаётся LLM». Логика «писать всё на диск для отладки» противоречит этому подходу.
- Аудит-trail (P2 в roadmap) делается отдельным механизмом, не побочным эффектом тула.

## Требования

### Functional Requirements

- **FR-001**: `analyze_perl_critic` НЕ ДОЛЖЕН создавать файлы на диске кроме временного `.pl` для подачи в `perlcritic` (этот временный файл — единственный, и он удаляется в конце вызова).
- **FR-002**: Поле `report_file` в возвращаемом dict ДОЛЖНО быть либо удалено из ответа, либо явно `None`. Клиенты тула не должны рассчитывать на наличие файла на диске.
- **FR-003**: Изменения НЕ ДОЛЖНЫ ломать существующий контракт ответа для других полей (`path`, `type`, `issues`, `count`, `error`, `timestamp`).

### Что НЕ входит в эту спеку

- **Race condition по имени временного `.pl` файла** (несколько одновременных запросов с одинаковым `filename` перетирают друг друга) — отдельная P1-задача, см. follow-up.
- **Path traversal через параметр `filename`** (`filename="../etc/passwd"`) — отдельная P1-задача.
- **Ограничение размера параметра `code`** — отдельная P2-задача.
- **Audit trail** (если когда-то нужен) — отдельный механизм, не побочный эффект `perlcritic`.

## Success Criteria

- **SC-001**: После 100 последовательных вызовов `perlcritic_analyze` (curl-скрипт) в контейнере нет файлов `/tmp/perlcritic_report_*.json`.
- **SC-002**: Существующий `test_server.py` проходит без изменений ассертов на структурные поля ответа.
- **SC-003**: `pr-reviewer-bot` и pre-push хук продолжают работать (они читают только JSON-RPC ответ, не файл).

## Assumptions

- Никто не читает `report_file` с диска снаружи. Это допущение подтверждается тем, что MCP-сервер удалённый — у клиентов в принципе нет к нему файлового доступа.
- Если в будущем понадобится сохранять артефакты для аудита — это будет отдельный механизм (P2 audit trail), не побочный эффект `perlcritic`.

## Риски

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Где-то внутри проекта код читает `report_file` | Низкая — удалённый режим | Грепнуть проект на `report_file` перед удалением поля |
| Тесты ассертят наличие `report_file` | Низкая | `test_server.py` ассертит на `issues`/`count`, поле `report_file` можно оставить как `None` для обратной совместимости |

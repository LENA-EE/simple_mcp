# Feature Specification: check_before_push

**Feature Branch**: `002-check-before-push`
**Created**: 2026-05-14
**Status**: Draft

## Контекст

"Husky для Perl" — автоматическая проверка кода перед попаданием в Bitbucket.
Джун делает `git push` → хук срабатывает локально на его машине → код уходит на
MCP-сервер → perlcritic анализирует → критичные нарушения блокируют пуш.

Цель: не пускать плохой Perl-код в Bitbucket. Локальные коммиты — дело джуна.

Разработчику не нужно ставить Perl::Critic — он работает в Docker на виртуалке банка.

**ВАЖНО: severity в Perl::Critic — шкала обратная:**
```
severity=1 → СТРОЖАЙШИЙ (стиль, всё подряд)
severity=2 → строгий
severity=3 → средние проблемы
severity=4 → серьёзные проблемы
severity=5 → КРИТИЧЕСКИЕ (опасный код)
```

**Логика принятия решения:**
```
severity 5 (критические)  → показать + БЛОКИРОВАТЬ пуш
severity 4 (серьёзные)    → показать + БЛОКИРОВАТЬ пуш
severity 3 (средние)      → показать как предупреждение, пуш идёт
severity 1-2 (стиль)      → не показывать вообще
```

## User Scenarios & Testing

### User Story 1 — Джун пушит код с критичной ошибкой (Priority: P1)

Джун написал `open(FILE, $path)` — двухаргументный open, security risk, severity=5.
Делает `git push`. Хук перехватывает, отправляет код на MCP, получает ответ.
Пуш заблокирован. Консоль показывает что именно не так и на какой строке.

**Why this priority**: Это основная ценность фичи — не пускать опасный код в Bitbucket
без участия сеньора.

**Independent Test**: Файл с `open(FILE, $path)`, вызов MCP-тула напрямую через curl,
проверить что `allow_push: false` и нарушение есть в ответе.

**Acceptance Scenarios**:

1. **Given** файл содержит `open(FILE, $path)` (severity=5), **When** хук вызывает `check_before_push`, **Then** `allow_push: false`, нарушение показано с номером строки, пуш не проходит.
2. **Given** файл содержит нарушение severity=4, **When** хук вызывает `check_before_push`, **Then** `allow_push: false`, нарушение показано.
3. **Given** файл чистый, **When** хук вызывает `check_before_push`, **Then** `allow_push: true`, пуш проходит без лишних сообщений.

---

### User Story 2 — Джун видит предупреждения но пуш не блокируется (Priority: P2)

Файл содержит нарушение severity=3. Пуш проходит, но джун видит предупреждение
в консоли — чтобы знал и исправил потом.

**Why this priority**: Баланс между строгостью и удобством. Блокировать на всё —
джун начнёт делать `git push --no-verify`.

**Independent Test**: Файл с нарушением severity=3, вызвать тул, убедиться что
`allow_push: true` и предупреждение присутствует в выводе.

**Acceptance Scenarios**:

1. **Given** файл содержит нарушение severity=3, **When** хук вызывает `check_before_push`, **Then** `allow_push: true`, нарушение показано с пометкой `⚠ WARNING`, пуш идёт.
2. **Given** файл содержит только нарушения severity=1-2, **When** хук вызывает `check_before_push`, **Then** `allow_push: true`, ничего не показывается, пуш идёт молча.

---

### User Story 3 — Несколько файлов изменено за один пуш (Priority: P2)

Джун меняет два `.pm` файла. Хук проверяет оба. Если хотя бы в одном критичная
ошибка — пуш заблокирован, в консоли видно в каком именно файле проблема.

**Why this priority**: Реальный сценарий — джун редко меняет ровно один файл.

**Independent Test**: Два файла, один чистый, другой с severity=5, передать оба в тул,
проверить что `allow_push: false` и указан нужный файл.

**Acceptance Scenarios**:

1. **Given** два файла: один чистый, второй с severity=5, **When** хук передаёт оба в `check_before_push`, **Then** `allow_push: false`, в выводе указано имя файла с проблемой.
2. **Given** два файла оба чистые, **When** хук передаёт оба, **Then** `allow_push: true`.

---

### User Story 4 — MCP-сервер недоступен (Priority: P3)

Виртуалка упала или нет сети. Хук не может достучаться до MCP.

**Why this priority**: Упавший сервер не должен парализовать работу команды.

**Independent Test**: Хук с неправильным URL, убедиться что пуш проходит и джун
видит предупреждение что проверка пропущена.

**Acceptance Scenarios**:

1. **Given** MCP-сервер недоступен, **When** хук пытается подключиться (таймаут 10с), **Then** `allow_push: true` (fail open), в консоли `⚠ MCP недоступен — проверка пропущена`.

---

### Edge Cases

- Нет изменённых `.pl`/`.pm` файлов в пуше → хук завершается молча, пуш идёт.
- Файл есть в git diff но удалён локально (например через `git rm`) → пропустить.
- Пустой файл → 0 нарушений, пуш идёт.
- Файл с синтаксической ошибкой Perl → perlcritic вернёт ошибку парсинга, показать разработчику как блокирующую.
- `git push --no-verify` → хук обходится, это ожидаемо, вне скоупа.

## Requirements

### Functional Requirements

- **FR-001**: MCP-тул `check_before_push` ДОЛЖЕН принимать `files: [{filename, code}]` и возвращать `{allow_push: bool, files: [...], message: str}`.
- **FR-002**: Блокировать пуш при наличии хотя бы одного нарушения severity 4 или 5 в любом из файлов.
- **FR-003**: Показывать нарушения severity 3 как предупреждения без блокировки.
- **FR-004**: Нарушения severity 1-2 не включать в ответ тула вообще.
- **FR-005**: При недоступности MCP хук ДОЛЖЕН пропускать проверку (fail open) и сообщать об этом.
- **FR-006**: Хук ДОЛЖЕН работать без Perl::Critic на машине разработчика.
- **FR-007**: Хук читает только изменённые `.pl` и `.pm` файлы относительно удалённой ветки.
- **FR-008**: Вывод в консоль: имя файла, номер строки, текст нарушения, для блокирующих — явный `❌ СТОП`.

### Key Entities

- **FileCheck**: `{filename: str, code: str}` — один файл для проверки.
- **FileResult**: `{filename, blockers: [], warnings: [], total: int}` — результат по файлу.
- **PushDecision**: `{allow_push: bool, files_checked: int, files: [FileResult], message: str}`.

---

## Success Criteria

- **SC-001**: Джун не может запушить файл с `open(FILE, $path)` — пуш блокируется автоматически.
- **SC-002**: Джун видит в консоли конкретную строку и что исправить — без гугления.
- **SC-003**: При чистом коде пуш проходит без лишних сообщений.
- **SC-004**: Падение MCP-сервера не блокирует работу команды.
- **SC-005**: Подключение к проекту — одна команда: `git config core.hooksPath .githooks`.

---

## Assumptions

- MCP-сервер уже запущен в Docker на виртуалке банка (порт 8000).
- `check_before_push` — обёртка над `perlcritic_analyze`, который уже работает.
- Машина разработчика имеет `bash` и `curl`.
- Кастомный `.perlcriticrc` с правилами проекта — вне скоупа этой спеки.
- Impact analysis (сломается ли что-то в другом файле) — вне скоупа, отдельная фича после Symbol Index.

## Что НЕ входит в эту спеку

- pre-commit hook — только pre-push (цель: не пускать в Bitbucket).
- Impact analysis зависимостей — требует `index.db`.
- Объяснения от Феникс/Qwen — только вывод из perlcritic.
- Серверный хук в Bitbucket — только клиентский хук на машине разработчика.

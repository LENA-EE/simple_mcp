# 1. 🎯 СКОУП ПРОДУКТА

## Описание проекта

- **Название:** DROSPR JARVIS (`mcp-drospr`)
- **Описание:** MCP-сервер для анализа легаси Perl-кода внутри банковского периметра. Разработчики подключаются из IDE через SSE, отправляют Perl-код, получают структурированный отчёт от Perl::Critic и символьную навигацию по проекту через PPI-индекс.
- **Целевой пользователь:** Perl-разработчик банка, работающий с легаси-кодом из IDE (Kilo / opencode); PR-ревьюер-бот, работающий с Bitbucket вебхуками.

---

## Скоуп MVP (≤5 пунктов)

1. Анализ Perl-кода через Perl::Critic с маппингом severity в человекочитаемые рекомендации (`perlcritic_analyze`).
2. Pre-push git-хук, блокирующий push при severity ≥ 4 (`check_before_push`).
3. PPI-индекс символов: `lookup_symbol`, `get_file_structure`, `get_callers`, `index_status`.
4. Загрузка индекса по защищённому эндпоинту (`POST /index/upload`, Bearer-токен), атомарная замена SQLite.
5. Docker-дистрибуция (`lenchik8/simple_mcp`) для развёртывания на банковской виртуалке.

---

## Что НЕ входит

❌ Доступ к файловой системе разработчика (MCP всегда работает удалённо — только параметр `code`).
❌ Анализ языков кроме Perl.
❌ Хранение истории/blame — это зона ответственности `mcp-bitbucket`.
❌ Семантический поиск (RAG) — отложен до того, как структурного индекса станет недостаточно.
❌ IDE-плагины — оркестрация остаётся на стороне IDE (Kilo / opencode).
❌ Прямое редактирование кода разработчика — агент только предлагает патч.

# 2. 🛠️ ТЕХНОЛОГИЧЕСКИЙ СТЕК

## Компоненты

### MCP-сервер (`server.py`)

- **Тип:** HTTP-сервис с SSE-транспортом, JSON-RPC 2.0
- **Язык:** Python 3.11+
- **Фреймворк:** FastAPI
- **Ключевые зависимости:** `fastapi`, `uvicorn`, `mcp` (см. `pyproject.toml`)
- **Хранилище:** SQLite (`data/index.db`) — PPI-индекс

### Анализатор кода (`tools/perlcritic.py`)

- **Тип:** Wrapper над внешним CLI
- **Язык:** Python (вызывает `perlcritic` через subprocess)
- **Кастомный verbose-формат:** `"%f\t%p\t%m\t%l\t%c\t%s\n"` (6 полей, TSV)
- **Зависимости:** `Perl::Critic` в контейнере; на машине разработчика **не нужен**

### Сборщик индекса (`tools/build_index.pl`)

- **Тип:** Offline-скрипт
- **Язык:** Perl
- **Зависимости:** `PPI`
- **Запуск:** на TeamCity-агенте по VCS Trigger
- **Контракт вывода:** JSON со схемой `functions / imports / globals / calls` — формат завязан на `index_store.py`, ломать без миграции нельзя

### Хранилище индекса (`tools/index_store.py`)

- **Тип:** SQLite-обёртка с атомарной заменой файла
- **Язык:** Python
- **Инвариант:** запись в `index_new.db`, затем `os.replace("index_new.db", "index.db")`

- **Пакетный менеджер:** pip (`pyproject.toml`, `pip install -e .`)
- **Рантайм / цель сборки:** Docker-образ (`lenchik8/simple_mcp:latest`)
- **Деплой:** виртуалка внутри банковского периметра, IP вида `192.168.x.x`

# 3. 📐 АРХИТЕКТУРА

## Архитектурный подход

- **Паттерн:** Harness over Model — `mcp-drospr` это детерминированный harness; LLM (Феникс/Qwen) подключается извне как заменяемый компонент.
- **Разделение слоёв:** транспорт (`server.py`) / тулы (`tools/perlcritic.py`, `tools/index_store.py`) / данные (`data/index.db`).
- **Изоляция API:** только два эндпоинта наружу — `GET /sse`, `POST /sse` для MCP-протокола; `POST /index/upload` для TeamCity (Bearer-токен).
- **Обработка ошибок:** агенту возвращается структурированный JSON; `raw_output` от `perlcritic` **никогда** не передаётся в LLM (засоряет контекст).

---

## Архитектура системы целиком

```
IDE (Kilo / opencode)
        ↓
MCP оркестрация
  ├── mcp-drospr (этот репо)
  │     ├── perlcritic_analyze   ← качество кода
  │     ├── lookup_symbol        ← где определена функция
  │     ├── get_file_structure   ← карта файла
  │     └── get_callers          ← кто вызывает функцию
  ├── mcp-bitbucket (отдельный репо)
  │     ├── git blame            ← кто и когда менял
  │     ├── commit history       ← почему так сделано
  │     └── file content         ← прочитать конкретные строки
  └── Феникс (Qwen, локальная LLM)
        ← получает только маленький точный контекст
        ← никогда не получает файл целиком
```

**Ключевой принцип разделения зон ответственности:**
PPI говорит **ЧТО** важно в файле, Bitbucket говорит **КТО и КОГДА** менял, Феникс **ДУМАЕТ** над полученным. Токены экономятся, галлюцинаций меньше.

| Вопрос | mcp-drospr (PPI) | mcp-bitbucket |
| --- | --- | --- |
| Где определена функция | ✅ | ❌ |
| Что импортирует модуль | ✅ | ❌ |
| Кто вызывает функцию | ✅ точно, из SQLite | ❌ text search — ловит и комментарии |
| Кто менял файл / git blame | ❌ | ✅ |
| Прочитать строки файла | ❌ | ✅ |

## Инженерные инварианты (нарушать нельзя без миграции)

**Severity в Perl::Critic — обратная шкала.** Об этом часто путаются и люди, и LLM:

```
severity=1 → СТРОЖАЙШИЙ (все нарушения, включая стиль)
severity=5 → только КРИТИЧЕСКИЕ
```

В коде блокируем push при `issue["severity"] >= 4`.

**Удалённый режим — всегда.** MCP-сервер работает в Docker на виртуалке банка, доступа к файловой системе разработчика **нет**:

- параметр `code` — работает всегда, передаётся строкой;
- параметр `target` (путь) — работает только если путь доступен внутри контейнера; в проде не использовать.

Агент/IDE читает файл локально и передаёт **содержимое** через `code`, а не путь.

**TSV verbose-формат `perlcritic`.** `tools/perlcritic.py` использует `"%f\t%p\t%m\t%l\t%c\t%s\n"`. Причина — дефолтный формат не содержит полного имени policy; `--verbose 5` ломал regex на одиночных файлах. TSV: 6 полей, предсказуемо.

**`raw_output` намеренно не отдаётся в LLM** — это решение уровня контекст-инженерии (AI DISRUPT v3.5 §2.10). Только структурированные `issues`.

**Регистрация тулов на старте.**

- `PERLCRITIC_AVAILABLE` — флаг модульного уровня; если `perlcritic` не в PATH, `perlcritic_analyze` **не регистрируется** в `tools/list`. Ожидаемое поведение для локальной разработки без Perl.
- `lookup_symbol / get_file_structure / get_callers / index_status` регистрируются только при наличии `data/index.db`.

**Атомарная замена индекса.** Пишем в `index_new.db`, затем `os.replace`. Читающие запросы не видят полуготовый индекс. Менять алгоритм без эквивалентной гарантии запрещено.

**Поток вызова тула:**

```
IDE → POST /sse {"method":"tools/call","params":{"name":"perlcritic_analyze","arguments":{"code":"..."}}}
  → handle_mcp_request()
  → analyze_perl_critic(code=...)            # tools/perlcritic.py
      → запись code во временный файл
      → запуск perlcritic с TSV verbose
      → парсинг TSV → список issues
  → get_recommendation(policy)               # рекомендации на русском
  → JSON-RPC response (без raw_output)
```

# 4. 👤 ПОЛЬЗОВАТЕЛЬСКИЕ СЦЕНАРИИ

**Сценарий 1. Pre-push защита.**
Разработчик → выполняет `git push` → `.githooks/pre-push` читает изменённые `.pl`/`.pm`, вызывает `check_before_push` → severity 4–5 блокирует пуш, severity 3 — предупреждение, всё ниже — молча проходит.

**Сценарий 2. Символьная навигация из IDE.**
Разработчик в IDE → задаёт LLM-агенту вопрос «где определена `process_billing`?» → агент вызывает `lookup_symbol` → получает `файл + строка` из SQLite, **не** читая весь репозиторий.

**Сценарий 3. Impact analysis перед коммитом.**
Разработчик меняет функцию `get_rate` → агент вызывает `get_callers("get_rate")` → видит 12 вызовов → предупреждает о высоком риске обратной несовместимости до коммита.

**Сценарий 4. PR-ревью ботом.**
Bitbucket webhook → `pr-reviewer-bot` (отдельный сервис) читает diff → вызывает `perlcritic_analyze` этого MCP → пишет комментарии только по новым проблемам, технический долг (existing issues) игнорирует.

# 6. ⚡ НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

## Производительность

- **Латентность одного вызова тула:** < 3 сек P95 для файла < 500 строк
- **Размер контекста в ответе:** только структурированные `issues`, без `raw_output` — экономия ~30% токенов на ответе (AI DISRUPT §5.5)
- **PPI-индекс vs полное чтение файлов:** экономия ~95% токенов на символьных запросах

## Надёжность

- **Аптайм:** target 99% в рабочее время банка; downtime ночью допустим.
- **Сигнал работоспособности:** `GET /` отвечает 200; `tools/list` возвращает ожидаемый набор тулов с учётом `PERLCRITIC_AVAILABLE` и наличия `index.db`.
- **Восстановление:** контейнер stateless, кроме `data/index.db` (volume `mcp_data`); при потере индекса — повторный `POST /index/upload` с TeamCity, тулы индекса автоматически возвращаются в `tools/list` после загрузки.

# 8. 🗄️ ДОМЕННАЯ МОДЕЛЬ

PPI-индекс в SQLite:

```sql
CREATE TABLE functions (name TEXT, file TEXT, package TEXT, line_start INT, line_end INT);
CREATE TABLE imports   (file TEXT, module TEXT, type TEXT, line INT);
CREATE TABLE globals   (file TEXT, varname TEXT);
CREATE TABLE calls     (caller_file TEXT, caller_line INT, callee_name TEXT);

CREATE INDEX idx_symbol ON functions(name);
CREATE INDEX idx_callee ON calls(callee_name);
```

Отношения:

```
File 1:M Function
File 1:M Import
File 1:M Global
Function 1:M Call   (через callee_name → functions.name)
```

Сбор `calls` в `build_index.pl`: `PPI::Token::Word` перед `PPI::Structure::List` ловит статические вызовы (~70% реального). Динамика через `AUTOLOAD` / `can()` намеренно не покрывается.

# 9. 🚀 ДЕПЛОЙ

- **Платформа:** Docker на виртуалке внутри банковского периметра.
- **Образ:** `lenchik8/simple_mcp:latest` (Docker Hub).
- **Переменные окружения:**

  | Переменная | Обязательна | Назначение |
  | --- | --- | --- |
  | `MCP_INDEX_TOKEN` | для `/index/upload` | Bearer-токен загрузки PPI-индекса |

- **Команда запуска (продакшен):**

  ```bash
  docker run -d --name mcp-drospr \
    -p 8000:8000 \
    -e MCP_INDEX_TOKEN=<секрет> \
    -v mcp_data:/app/data \
    lenchik8/simple_mcp:latest
  ```

  `-v mcp_data:/app/data` — сохраняет `index.db` между перезапусками.

- **CI/CD:** TeamCity собирает PPI-индекс по VCS Trigger из Bitbucket и POST-ит на сервер. Сам Docker-образ собирается вручную и пушится на Hub (на момент L1).
- **Стратегия отката:** запуск предыдущего тега из Docker Hub (`lenchik8/simple_mcp:<prev>`); индекс переживает откат благодаря volume.

# 🧭 СТРАТЕГИЧЕСКИЙ КОНТЕКСТ

Документ-ориентир: **AI DISRUPT PDLC v3.5** (Кирилл Меньшов, апрель 2026). Архитектурные решения проекта мотивированы пятью принципами оттуда:

1. **Harness over Model (§2.2).** `mcp-drospr` — это harness; LLM (Феникс/Qwen) — заменяемая модель. Capital asset — harness, не модель.
2. **Context Engineering (§2.10).** PPI → точно отбирает, что важно; Bitbucket достаёт только нужное; Феникс получает ~70 строк вместо 2000. Экономия ~95% токенов.
3. **Двухпетлевая модель (§2.1).** Наша система — checkpoint между Intent Loop и Implementation Loop (PR-бот) и провайдер контекста внутри Implementation Loop (MCP-тулы).
4. **Токеномика (§5.5).** Perlcritic перед LLM −70%; PPI вместо чтения файлов −95%; убран `raw_output` −30%.
5. **Orchestrator-Workers (§2.9).** IDE = оркестратор; `mcp-drospr`, `mcp-bitbucket`, Феникс — воркеры.

**Дорожная карта зрелости:** L2 (AI-assisted, сейчас) → L3 (AI-augmented, цель: evals + audit trail + Guardian) → L4 (AI-native, горизонт).

# 🚫 АНТИПАТТЕРНЫ

❌ **Всё в один MCP-сервер.** Граница между `mcp-drospr` (структура кода), `mcp-bitbucket` (история и содержимое), `pr-reviewer-bot` (PR-воркфлоу) проведена намеренно — не нарушать.
❌ **Fine-tuning вместо context engineering.** Дорого, медленно, устаревает при смене модели. Сначала улучшать контекст.
❌ **Автоматическое применение изменений кода.** Агент предлагает патч → человек принимает → стандартный PR. Всегда.
❌ **Передача `raw_output` в LLM.** Засоряет контекст, теряется структура.
❌ **Использование `target` параметра в продовых потоках.** MCP всегда удалённый — пути разработчика недоступны.
